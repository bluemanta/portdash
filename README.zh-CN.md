# PortDash

本地开发服务的可视化控制台。零依赖单文件，只用 Node 自带模块。

[![tests](https://github.com/bluemanta/portdash/actions/workflows/test.yml/badge.svg)](https://github.com/bluemanta/portdash/actions/workflows/test.yml)

[English](README.md)

## 运行

```bash
npx @bluemanta/portdash
```

或者克隆下来直接跑：

```bash
git clone https://github.com/bluemanta/portdash.git
cd portdash
node portdash.js
```

然后打开 http://localhost:7777

也可以在访达里双击 `启动PortDash.command`。

## 让看门狗常驻（可选）

看门狗只在 PortDash 运行时才起作用。关掉它，你的 dev server 会继续跑——但没人看着。想让它常驻后台：

```bash
npm install -g @bluemanta/portdash
portdash --install-agent
```

这会装一个 macOS LaunchAgent，开机自启、异常退出后自动重启。它**以你自己的身份运行，不是 root**——发信号给你的进程需要同一个用户，而 root 的权限远超它的实际需要。卸载用 `portdash --uninstall-agent`。

两个需要知道的坑：

- 它会记下安装时那个 `node` 的路径。如果那是 nvm 管的版本，之后你把该版本删了，agent 就废了——重装一次，或者指向一个稳定的 Node。
- **被冻住的服务是安静的。** SIGSTOP 之后进程不崩溃、不报错，只是不响应，如果你忘了后台有东西在管着会很困惑。服务无缘无故没反应时，去看 `~/.portdash/portdash.log`。

## macOS 权限（完全磁盘访问、照片、通讯录……）

如果一个服务你在终端里跑得好好的，通过 PortDash 启动却报 `Operation not permitted`，原因在这里。

macOS 把隐私权限授予**责任进程**——也就是启动链最顶端的那个 App，而不是真正干活的那个二进制。子进程继承这个身份。进程被 detach、自成进程组**不会**切断继承，唯一起作用的是链顶是谁。

所以解法取决于 PortDash 自己是被谁启动的：

| PortDash 的启动方式 | 责任进程 | 怎么办 |
|---|---|---|
| Terminal.app / iTerm | 该终端 | 不用管——直接继承你已经授给终端的权限 |
| 别的 App（编辑器、AI agent、启动器） | 那个 App | 给那个 App 授权，或者改从终端启动 PortDash |
| `--install-agent` | `node` 二进制本身 | 直接给 `node` 授权 |

常驻 agent 模式下没有终端可继承，所以要授权给 Node 本身：
系统设置 → 隐私与安全性 → 完全磁盘访问权限 → `+` → <kbd>⌘⇧G</kbd> → 填 `which node` 的输出。

授权前需要权衡两点：

- 这等于给你机器上**所有** Node 程序都开了这个权限，不只是 PortDash。授权面比大多数人预期的宽，而 macOS 在这里没有更细的粒度。
- 用一个稳定的解释器路径。nvm、asdf 这类版本管理器每次升级都会换路径，授权不会跟着走。

## 它能做什么

- **看**：所有正在监听端口的进程，按项目归类；每个项目显示实时内存占用
- **控**：启动 / 暂停 / 恢复 / 重启 / 停止，信号发给整个进程组，`npm run dev` 派生的子进程一起收
- **暂停是真暂停**：SIGSTOP 挂起，进程冻在原地，内存和端口都保留，恢复（SIGCONT）是瞬间的
- **置顶**：每天都要开的那几个，点 ☆ 钉到顶部独立区域；不管有没有在跑，位置不变，地址都能点开
- **日志**：由 PortDash 启动的服务，输出记在 `~/.portdash/logs/`，界面上直接看
- **外部启动也认**：你在终端里手动跑的 dev server，只要工作目录对得上，也显示在对应项目下并可被停掉
- **说清每个服务归谁管**：是从哪个终端、编辑器或脚本起来的，还是由哪个 launchd job 托管。被 launchd 托管的服务在任何面板上都停不掉——停完一秒就回来——所以那种行不再给一个按了像没反应的按钮，而是直接给出真正管用的命令（`brew services stop postgresql@16`）
- **launchd 托管的服务可以直接重启**，而这通常才是你真正想要的：常驻的 LaunchAgent 要重启一次才能吃到新代码，PortDash 不会自己停掉再起一份，而是交给 launchd 去做（`launchctl kickstart -k`）。停旧的和起新的是 launchd 的同一个动作，中间没有让两份同时跑起来的空隙。macOS 自带的 agent 和其它地方一样，不在此列
- **用你自己的环境启动服务**：PortDash 启动时读取你 shell 的真实环境，所以装在 nvm / Homebrew / Volta / asdf / pyenv 里的工具它都看得见 —— 哪怕它自己是作为后台登录代理运行的（那种情况下继承到的 PATH 几乎是空的）
- **失败会说清原因**：服务启动即崩时会弹出提示，直接指出是命令找不到、端口被占、还是依赖没装，而不是把原因留在日志文件里等你去翻
- **环境自检面板**：显示 PortDash 实际能看到什么（shell、node、npm、pnpm、yarn、bun、python3、git，以及完整 PATH），带"重新检测"按钮。报问题时截这一张图就够了
- **"在跑"不等于"能用"**：绿点以前只代表进程存在。现在它去问端口——还在编译的 dev server 显示"启动中"，端口开着但从不应答的显示"无应答"，只有真的收到回复才是"可用"。任何 HTTP 响应都算活着，404 和 500 也算：根路径返回 404 说明服务器起来了、路由在工作。判定为不说 HTTP 的端口，之后只做 TCP 连接——否则你把数据库登记成项目，它会每几秒往自己日志里收一条协议错误
- **端口它不会凭空捏造**："默认端口"是 PortDash 用来打开、置顶和检查的地址，**它不改变你的程序监听在哪里**，编辑框里也写明了这点。项目记录了端口的话，启动前它会确认那个端口没被别人占着，占了就指名是谁，而不是让启动在子进程里以 `EADDRINUSE` 失败。扫描发现的静态站每个分到自己的端口，不再全部写成 `8000`
- **同一个仓库跑两个服务**——比如一个本地环境常年开着，旁边再跑一个测试环境。两个各占一行，各有自己的内存上限和 Stop 按钮：第二个从"other ports in use"里注册进来，靠端口和第一个区分开。项目记录的端口同时也决定了某一行代表的是哪个服务——在此之前，行只按目录匹配，谁排在前面就认谁，于是同一个按钮作用在哪个服务上会在重启之间悄悄变掉，屏幕上没有任何提示
- **别人的程序归别人**："其它进程"段仍然列出所有监听端口的进程，但只对**可能是你的**那些提供停止操作。macOS 自己的 agent 和正在用的应用完全没有启停按钮——ControlCenter 占着 `:5000`，那一行上的"暂停"就是对你的菜单栏发 SIGSTOP

## 内存保护（防止某个服务把整台机器拖死）

看门狗每 2 秒扫一次全系统进程表，五道闸门：

| 闸门 | 触发条件 | 动作 |
|---|---|---|
| Node 堆上限 | 启动时注入 `NODE_OPTIONS=--max-old-space-size` | 让 node 自己 OOM 退出，而不是吃光系统内存 |
| 单项目软上限 | 进程组内存 > `projectRssMB`（默认 4G），且该项目没被豁免 | SIGSTOP 冻结，保留现场，告警里带着出路 |
| 单项目硬上限 | > `hardRssMB`（默认 10G） | 直接 SIGKILL，不再客气 |
| 系统水位 | 可用内存 < 12%，或 swap 用量 > 4G | 冻结当前最占内存的项目；如果元凶不是 PortDash 起的，只告警 |
| 启动闸门 | 内存已紧张 / 60 秒内同一项目启动超过 3 次 | 拒绝启动，提示先看日志 |

**冻结不是杀死**：进程还在，内存和端口都还占着；看完日志你可以恢复继续，或者停止收工。

宣布冻结的那条告警自带两条出路。**恢复**把它原样放回去。第二个按钮——用默认 4G 上限的项目上显示为 **Allow 8.0G and resume**，因为它给的是当前上限的两倍——把这个项目自己的上限抬高再解冻，**一步完成**。分两步做的话，解冻时它还超着限，两秒后会被再冻一次。

对于那种本来就会吃内存的东西——扫描、导入、长构建——「编辑」里的**「永不自动冻结这个」**可以彻底关掉它自己的上限。硬上限仍然生效（那是防止跑飞的进程拖死机器的最后一道），系统水位那道也仍然生效：后者判断的是机器的事实，不是对你这个项目的猜测。

阈值都在 `~/.portdash/config.json` 的 `limits` 里改，单个项目还能在界面上单独设。
嫌它管太宽就把 `limits.enabled` 设成 `false`。

## 配置

都在 `~/.portdash/` 下：

| 文件 | 作用 |
|---|---|
| `config.json` | 扫描目录 `scanRoots`、界面端口 `uiPort`、扫描深度 `scanDepth`、内存限额 `limits`，以及一个服务最多可以多久没应答才不再被算作"启动中"（`readyGraceSec`，默认 60 秒——你这台机器上冷启动构建确实更慢就调大它） |
| `projects.json` | 项目登记表。首次运行自动扫描生成，之后「重新扫描」只增不改 |
| `state.json` | PortDash 拉起的进程记录 |
| `token` | API 令牌，首次运行生成，权限 `0600` |
| `portdash.log` | PortDash 自己的输出，超过 2M 自动轮转 |
| `logs/` | 每个项目一个日志文件，启动时超过 5M 自动归档为 .old |

启动命令是扫描时从 `package.json` 的 scripts 猜的（dev > start > serve），猜错了在界面上点「编辑」改掉，之后不会被覆盖。

## 安全

这个 API 能拉起进程，所以做了三层限制：`Host` 头必须是本地（挡 DNS 重绑定）、跨站 `Origin` 一律拒绝、所有 `/api/` 请求必须带上 `~/.portdash/token` 里的令牌（放在 `X-Portdash-Token` 头里）。前两层挡的是网页，令牌挡的是**本机其他进程**——常驻之后这一层才是关键。

脚本调用的话：

```bash
curl -H "X-Portdash-Token: $(cat ~/.portdash/token)" http://localhost:7777/api/state
```

## 注意

- 关掉 PortDash 不会影响已经启动的服务，它们继续在后台跑；重开会重新认领它们
- 看门狗只自动处置 PortDash 自己启动的进程，不会去动你手动跑的东西
- pid 会被系统回收，所以一条记录只有在占用该 pid 的进程「年龄不小于记录本身」时才被信任，否则宁可丢弃，也不冒险对陌生进程发信号
- 端口被占时它会等待重试而不是退出，而且只有抢到端口之后才启动看门狗。它也认得出机器上任何位置的另一个 PortDash：两个共用同一份 `~/.portdash` 时，**运行更久的那个留守看门狗**，新起的那个只负责显示面板，所以它们不会各自去冻结同一批进程，也不会互相覆盖记录
- 界面只监听 127.0.0.1，不对局域网开放

## 开发

```bash
npm test
```

两层。`test.js` 直接调用小零件——记录的都是代码上看不出来的决定，比如为什么应用要按 bundle 名而不是里面那个二进制来命名，或者为什么某一行必须排在另一行前面。`test-http.js` 把真的 PortDash 作为子进程启动、走 HTTP 驱动它，只有这一层看得见"某个同步调用把整个面板冻住"这类问题——那不是任何单个函数算错了。

测试**绝不碰你真实的 `~/.portdash`**（子进程拿到的是临时 HOME 和一个当场造出来的项目），沙箱里的内存阈值调得足够高，看门狗照常运行、照常采样，但永远够不到阈值——所以这套测试没有任何办法对运行它的机器发信号。

内置测试运行器需要 Node 18 以上。PortDash 自己仍然能在 16 上跑，而且这些文件不会发布：`package.json` 的 `files` 字段决定了进 npm 包的是哪些。
